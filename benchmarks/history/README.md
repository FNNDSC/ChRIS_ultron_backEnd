# Benchmark History — committed milestone runs

This directory holds the **small, committed artifacts** of milestone benchmark runs
(`summary.json`, `environment.json`, `levels.jsonl`, `report.md` per run — a few KB each),
populated by `just bench-archive <run_id>`. The full raw runs live in `../results/`
(gitignored). Control-plane Locust CSVs + a generated RED report are under `locust/`.

**Start here:** the human-facing narrative is [`../REPORT.md`](../REPORT.md) — it unifies the
data plane (this dir's per-run reports) and the control plane (`locust/`) **by finding**
(concurrency, latency, bottlenecks, …), not by tool. The tables below are the index that
maps each archived artifact to the finding it backs; open a run's `report.md` to drill in.

## How these results were generated

All runs used the pinned envelope (`envelope.md`), `fslink` storage, on the dedicated Linux box,
and `dbg-bigfiles` 1.0.0, `pl-simpledsapp` 2.1.5, and `pl-topologicalcopy` 1.0.13. Since the
committed pin (`benchmarks/chrisomatic/benchmark.yml`, `envelope.md` § "Pinned workload plugin
versions") `just bench-start` registers those versions and the harness refuses to start against
any other registration; earlier campaigns registered them from `chrisomatic/chrisomatic.yml`,
edited locally or as committed at the time, as noted with each below (the June runs record no
plugin versions or images, and the file committed then, 94e585d, took `pl-topologicalcopy` by
name from the ChRIS store). Two conventions matter for reproducing them faithfully:

- **Clean-stack discipline.** Isolation runs are preceded by a recovery so a prior failure
  can't contaminate them (we saw spurious failures otherwise). A light reset is a service
  restart; a full reset (wipes the DB) is
  `just bench-compose '--profile cube --profile bench down -v'`, then removing the plugin-job
  containers (`docker ps -aq --filter label=org.chrisproject.miniChRIS=plugininstance | xargs -r
  docker rm -f`), then `just bench-start`.
  The `--profile` flags are required — without them the profile-scoped `chris`/workers are
  *not* torn down, leaving an old `chris` against a fresh DB (chrisomatic then fails). A fresh
  DB numbers plugin instances from 1 again, so job containers a previous stack left behind
  would collide with the new jobs' names (`chris-jid-<id>`) in pfcon.
- **Poll interval** is a service env var; changing it needs a recreate:
  `CUBE_CELERY_POLL_INTERVAL=N just bench-compose 'up -d --force-recreate chris worker-mains worker-periodic celery-scheduler'`.

```bash
# Full sweep (022252Z) — authoritative breaking points, all axes/topologies
just bench-start
just bench-run --tier full

# Isolated diamond·feeds (153019Z) — confirm the full-sweep L1 fail was contamination
just bench-compose 'restart chris worker-mains worker-periodic celery-scheduler'
just bench-run --tier full --topology diamond --axis feeds --restart-on-fail

# Long-active-job class (155156Z linear, 162609Z fanout) — hold a 60s job, escalate feeds
just bench-compose 'restart chris worker-mains worker-periodic celery-scheduler'
just bench-run --tier full --topology linear       --axis feeds --sleep-length 60 --repeat 1 --restart-on-fail
just bench-compose 'restart chris worker-mains worker-periodic celery-scheduler'
just bench-run --tier full --topology fanout_fanin --axis feeds --sleep-length 60 --repeat 1 --restart-on-fail

# State-aging loop (probes 165243Z…190409Z) — NO restart between cycles (DB must accumulate)
just bench-compose 'restart chris worker-mains worker-periodic celery-scheduler'
just bench-run --tier aging-probe                                   # baseline @ ~0 rows
just bench-run --tier aging-grow  --no-cleanup                      # +~56k rows; repeat probe/grow…
just bench-run --tier aging-grow  --no-cleanup --file-count 10000   # +~560k rows/grow (toward millions)

# Diamond·layers clean confirm (192652Z) — fresh stack rules out host-state amplification
just bench-compose '--profile cube --profile bench down -v' && just bench-start
just bench-run --tier full --topology diamond --axis layers --cap 16 --repeat 1 --restart-on-fail

# Poll-interval sweep, sleep=0 (224601/224933/225520Z) and sleep=60 (234231/235952/2026-06-17T001826Z)
just bench-compose '--profile cube --profile bench down -v' && just bench-start
for pi in 2 4 8; do
  CUBE_CELERY_POLL_INTERVAL=$pi just bench-compose 'up -d --force-recreate chris worker-mains worker-periodic celery-scheduler'
  CUBE_CELERY_POLL_INTERVAL=$pi just bench-run --tier full --topology linear --axis depth --cap 16 --repeat 1 --restart-on-fail
  # sleep=60 variant: add `--sleep-length 60 --cap 8`
done

# File-size 2-point sanity (230851Z 1KiB, 231046Z 1MiB), poll=2
just bench-run --tier full --topology linear --axis depth --cap 8 --repeat 1
just bench-run --tier full --topology linear --axis depth --cap 8 --repeat 1 --file-size 1MiB

# Control-plane RED (locust/) — read saturation sweep + opt-in write run
for u in 25 50 100 200 400; do just bench-locust "-u $u -r $u -t 90s --csv /app/benchmarks/results/locust/read_u$u"; done
BENCH_LOCUST_WRITE=1 just bench-locust '-u 10 -r 5 -t 60s --csv /app/benchmarks/results/locust/write_clean_u10'
```

## Post-upgrade baseline — 2026-09-17 (commit 30fbbaf)

Every analysis the issue set cites was re-run after the Django 6.0 / DRF 3.18 upgrade, one run per
benchmark command the issue set uses, so each claim has a baseline produced by the same invocation.
`bench-compare` calls two runs comparable only when their workload fingerprints match, and the
fingerprint covers `--topology`, `--axis` and `--cap` but not `--repeat` — so these, not the June
runs, are what a candidate fix should be compared against. See [`../REPORT.md`](../REPORT.md) §13
for what reproduced, what moved and the corrections these runs produced.

Host and stack differences from June: Docker 27.3 → 29.8, kernel 7.0.0-22 → 7.0.0-31, Django
6.0.8, DRF 3.18.1, Celery 5.6.3, psycopg 3.3.5, PostgreSQL 18.2. These runs used `pl-topologicalcopy`
1.0.13, `pl-simpledsapp` 2.1.5 and `dbg-bigfiles` 1.0.0, registered from a locally edited
`chrisomatic/chrisomatic.yml`; that edit is deliberately not committed, because the dev environment
should not be stuck at the benchmark's plugin versions. The ChRIS store now serves
`pl-topologicalcopy` 2.0.0 — a no-op image — under the name the harness resolves, so reproducing
these runs needed that edit. Since the committed pin ([`../envelope.md`](../envelope.md)
§ "Pinned workload plugin versions") `just bench-start` registers the same versions, and
`bench-compare` compares `workload_plugins`, which it did not when these runs were made.

### Control plane

[`locust_2026-09-17/`](locust_2026-09-17) holds `fresh/` (read sweep 25–400 users on a nearly

### Reproducing these

```bash
# One targeted run per command, on a clean stack, in the order above
just bench-compose '--profile cube --profile bench down -v' && just bench-start
just bench-run --tier full --topology linear --axis depth --cap 64 --repeat 1 --restart-on-fail

# The duplicate-submission reproducer (fails in every attempt)
just bench-run --tier full --topology fanout_fanin --axis branches --cap 64 --file-count 1000 \
    --repeat 1 --restart-on-fail

# Fault injection: start the run, then disturb pfcon 8 s after levels.jsonl gets its feeds=8 row
just bench-run --tier full --topology fanout_fanin --axis feeds --cap 16 --repeat 1 --restart-on-fail &
just bench-compose 'restart pfcon'        # or: pause/unpause, stop/start

# Control plane, fresh then aged (the aged sweep needs the aging series to have run first).
# On 2026-09-17 the pools did not recover after a step from 100 users up, so chris had to be
# restarted between steps; since the fix (locust_2026-10-06) each step checks it by itself.
for u in 25 50 100 200 400; do just bench-locust "-u $u -r $u -t 90s --csv /app/benchmarks/results/locust/read_u$u"; done
BENCH_LOCUST_WRITE=1 just bench-locust '-u 10 -r 5 -t 60s --csv /app/benchmarks/results/locust/write_u10'
```

During the campaign `BENCH_LOCUST_WRITE` did not reach the `benchmark` container, so the first
write-path run had no create requests and `write_create_u10` was run with `run --rm -e
BENCH_LOCUST_WRITE=1 ...`. `docker-compose.benchmark.yml` passes the variable through since
2026-09-18. Scenario `pg_stats.json` files of these runs hold only the 15 most expensive statements;
the harness keeps all of them since the same date. The compose service is `pfcon`; `pfcon.remote`
is only its network alias.
